# 摆摊记账 APP 底部输入框接手说明

这份文档只讲一件事：把现有 Jotly 的底部输入框，最快、最稳、最少沟通成本地移植到一个新的「摆摊记账」APP 里。

## 源项目地址

- 源项目根目录：`/Users/gaoxingchen/Documents/Jotly/Jotly`
- 先看这几个文件：
  - `Jotly/JotlyHomeScreen.swift`
  - `Jotly/JotlyHomeViewModel.swift`
  - `Jotly/JotlyServices.swift`
  - `Jotly/JotlyModels.swift`
  - `Jotly/CloudASRServices.swift`
  - `Jotly/MimoASRService.swift`

## 目标

- 新 APP 只保留和摆摊记账相关的内容
- 底部输入框必须保留，且作为主入口
- 输入框的交互、状态和语音能力尽量沿用当前实现
- 不扩展无关功能，不重做一套新的输入体系

## 最小接入方式

直接复用现有的底部输入框结构，不要重新设计交互，不要重讲产品逻辑。

对接手方来说，最重要的是先把这块原样搬过去：

保留这些东西：

- 底部固定输入栏
- 长按说话
- 实时转写
- 提交按钮或发送动作
- 语音转写结果回填
- 选项确认 / 纠错入口

先别加这些东西：

- 多层复杂导航
- 与记账无关的首页信息流
- 过多快捷入口
- 额外装饰性的输入模式

## 最短迁移顺序

1. 先把底部输入框所在的视图搬过去
2. 再把 `ViewModel` 和状态机搬过去
3. 再把 4 条语音链路的入口接上
4. 再补依赖的模型、服务和持久化
5. 最后才考虑外观细调

## 复制优先级

如果目标项目想省时间，优先直接挪这几类代码，而不是重写：

- 底部输入框视图
- 输入状态管理
- 实时转写合并逻辑
- 语音服务切换逻辑
- 识别结果回填逻辑
- 记账相关的提交动作

## 四条调用链路

这 4 条链路都保留，后续只是按场景切换，不要删掉：

1. `Apple`
2. `MIMO`
3. `豆包`
4. `阿里`

### 统一规则

- 4 条链路对外都只输出一套统一结果
- 临时结果只替换当前临时句，不要追加
- 最终结果只提交一次
- UI 层不要关心具体厂商细节

### 你可以把它理解成

- `Apple`：系统原生，适合快速验证
- `MIMO`：适合做对照和备用方案
- `豆包`：实时链路，适合主测
- `阿里`：实时链路，适合主测

## 底部输入框需要的能力

这个输入框至少要有以下能力：

- 录音开始时立刻有反馈
- 波形立即动，不等云端返回
- 转写文字实时回显
- 同一句话修正版不要重复叠加
- 说完后能稳定提交一条记录
- 出错时能回退到纯文本输入

## 关键原则

- 先搬代码，再改样式
- 先复用现成输入框，再谈新产品
- 先统一语音结果语义，再调各家 SDK
- 不要让目标产品自己重新发明一套输入框
